# Phase 4.1: Image Standardization & Print Area Detection - Research

**Researched:** 2026-03-11
**Domain:** Node.js image processing — garment boundary detection, canvas normalization, coordinate derivation
**Confidence:** HIGH

## Summary

The core problem has two parts that share a single root cause: supplier images arrive with inconsistent garment-to-canvas ratios. A simple `fit: contain` resize scales the whole image uniformly, which means the garment may sit at 40% of canvas height on one product and 70% on another. The fixed percentage-based print area coordinates (`PRINT_AREA_COORDINATES` in `variants.ts`) were calibrated against the reference images (S05280, L00550), so any garment that deviates from those proportions will have the print box misaligned.

The solution is to detect the garment's actual bounding box within each source image, then reposition and scale the garment so it occupies the same fraction of the 2000×2000 canvas as the reference image does. Once the garment is consistently placed, the print area box — derived as a fixed fraction of the garment bounding box — will land in the right place every time. This replaces two hardcoded coordinate tables with dynamically computed coordinates per-image.

The entire approach is achievable with `sharp` alone (already a project dependency), using `trim()` with `toBuffer({ resolveWithObject: true })` to extract `trimOffsetLeft`, `trimOffsetTop`, and post-trim dimensions. No new dependencies are required for the basic approach. An ML-based background removal library (`@imgly/background-removal-node`) exists as an upgrade path for garments with complex or dark backgrounds, but introduces a ~40 MB ONNX model download and 2-5 second per-image latency, which is overkill for standard white-background supplier images.

**Primary recommendation:** Use `sharp.trim()` with threshold tuning to extract the garment bounding box, derive target placement from the reference garment-to-canvas ratio, composite onto a clean 2000×2000 white canvas, and compute print area coordinates as fractions of the placed garment bounds. This keeps the dependency tree unchanged and processes each image in under 100ms.

### Pattern 1: Garment Bounding Box via sharp.trim()

**What:** Call `trim()` on the source image with a white-background threshold, then read `trimOffsetLeft`, `trimOffsetTop`, plus the trimmed width/height from the info object.

**When to use:** Source images have plain white or near-white backgrounds (standard for CSW and S&S Canada supplier images).

**Example:**
```typescript
// Source: sharp docs + github.com/lovell/sharp/issues/2396

async function detectGarmentBounds(imageBuffer: Buffer): Promise<{
  offsetLeft: number;
  offsetTop: number;
  width: number;
  height: number;
  originalWidth: number;
  originalHeight: number;
}> {
  // First get original dimensions
  const meta = await sharp(imageBuffer).metadata();
  const originalWidth = meta.width!;
  const originalHeight = meta.height!;

  // Trim white background (threshold=10 handles near-white pixels)
  const { data, info } = await sharp(imageBuffer)
    .trim({ background: '#ffffff', threshold: 10 })
    .toBuffer({ resolveWithObject: true });

  return {
    offsetLeft: Math.abs(info.trimOffsetLeft ?? 0),
    offsetTop: Math.abs(info.trimOffsetTop ?? 0),
    width: info.width,
    height: info.height,
    originalWidth,
    originalHeight,
  };
}
```

### Pattern 2: Place Garment at Reference Ratio

**What:** After detecting the garment bounding box, scale and composite the garment onto a 2000×2000 white canvas so the garment occupies the same fraction of canvas height as it does in the reference image.

**When to use:** Always — after trimming the garment out of the source image.

**Reference ratios (measured from reference images):**
- Tops (S05280): garment height = ~73% of 2000px = ~1460px; garment vertical offset from top = ~6% = ~120px
- Hoodies (L00550): garment height = ~78% of 2000px = ~1560px; garment vertical offset from top = ~5% = ~100px

These ratios define the target placement. Any supplier image is scaled so its trimmed garment height matches this target height, then composited at the target top offset.

```typescript
// Source: sharp docs (api-composite, api-resize)

async function placeGarmentOnCanvas(
  garmentBuffer: Buffer,        // the trimmed garment (any size)
  targetHeightPx: number,       // e.g. 1460 for tops
  targetTopOffsetPx: number,    // e.g. 120 for tops
  canvasSize = 2000,
): Promise<Buffer> {
  const garmentMeta = await sharp(garmentBuffer).metadata();
  const aspectRatio = garmentMeta.width! / garmentMeta.height!;
  const scaledWidth = Math.round(targetHeightPx * aspectRatio);
  const leftOffset = Math.round((canvasSize - scaledWidth) / 2);

  const resized = await sharp(garmentBuffer)
    .resize(scaledWidth, targetHeightPx, { fit: 'fill' })
    .toBuffer();

  return sharp({
    create: {
      width: canvasSize,
      height: canvasSize,
      channels: 3,
      background: { r: 255, g: 255, b: 255 },
    },
  })
    .composite([{ input: resized, left: leftOffset, top: targetTopOffsetPx }])
    .png()
    .toBuffer();
}
```

### Pattern 3: Derive Print Area Coordinates from Placed Garment

**What:** Once we know where the garment sits on the 2000×2000 canvas (left offset, top offset, width, height), express the print area box as a fraction of those dimensions and convert to percentages.

**When to use:** Always, replacing the hardcoded `PRINT_AREA_COORDINATES` tables.

**Print area fractions (derived from reference images, both top categories):**

For the front print area on a t-shirt, the printable chest zone starts roughly:
- 10% down from the garment's top edge (below the neckline)
- 15% in from the garment's left edge
- spans 70% of garment width
- spans 55% of garment height

These fractions stay constant — they represent "where the chest is relative to the garment", regardless of how the garment is scaled on canvas.

```typescript
// Print area fractions per category group (relative to garment bounding box, not canvas)
// These should be validated against the reference images once the pipeline is running

const GARMENT_RELATIVE_PRINT_FRACTIONS = {
  tops: {
    'Front Print': { xFrac: 0.15, yFrac: 0.10, wFrac: 0.70, hFrac: 0.55 },
    'Back Print':  { xFrac: 0.13, yFrac: 0.10, wFrac: 0.74, hFrac: 0.53 },
  },
  hoodies: {
    'Front Print': { xFrac: 0.20, yFrac: 0.28, wFrac: 0.60, hFrac: 0.40 },
    'Back Print':  { xFrac: 0.18, yFrac: 0.35, wFrac: 0.64, hFrac: 0.43 },
  },
} as const;

function derivePrintAreaCoords(
  garmentLeftPx: number,
  garmentTopPx: number,
  garmentWidthPx: number,
  garmentHeightPx: number,
  categoryGroup: 'tops' | 'hoodies',
  canvasSize = 2000,
): Record<string, { x: string; y: string; width: string; height: string }> {
  const fractions = GARMENT_RELATIVE_PRINT_FRACTIONS[categoryGroup];
  const result: Record<string, { x: string; y: string; width: string; height: string }> = {};

  for (const [printArea, frac] of Object.entries(fractions)) {
    const x = garmentLeftPx + frac.xFrac * garmentWidthPx;
    const y = garmentTopPx + frac.yFrac * garmentHeightPx;
    const w = frac.wFrac * garmentWidthPx;
    const h = frac.hFrac * garmentHeightPx;

    result[printArea] = {
      x: ((x / canvasSize) * 100).toFixed(2),
      y: ((y / canvasSize) * 100).toFixed(2),
      width: ((w / canvasSize) * 100).toFixed(2),
      height: ((h / canvasSize) * 100).toFixed(2),
    };
  }

  return result;
}
```

The front image drives print area coord derivation (front image gives garment placement after trimming/compositing). Back image is standardized the same way but uses the back print area fractions.

### Anti-Patterns to Avoid

- **Using `fit: contain` without trim:** Does not normalize garment position — just scales the whole original image. The garment may be at any position on the result canvas.
- **Single threshold value:** White-background images often have shadows or slight off-white pixels. Use `threshold: 10` (not 0). If artifacts appear, tune up to 20-30.
- **Calling `trim()` without `toBuffer({ resolveWithObject: true })`:** The offset properties (`trimOffsetLeft`, `trimOffsetTop`) are only available on the info object returned by `toBuffer()` or `toFile()`, not on the sharp instance.
- **Trusting raw trimOffsetLeft sign:** According to sharp issue #4084 (April 2024), the sign can be negative depending on the trim direction — use `Math.abs()`.
- **Running trim on side/lifestyle images:** Side view images often have non-white elements (shadows, models). Only run the garment detection pipeline on front and back product flat-lay images.
- **Hard-coding print fraction constants without visual validation:** The fractions in `GARMENT_RELATIVE_PRINT_FRACTIONS` above are derived estimates. They MUST be visually validated against real products before treating as final.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| White background detection | Custom pixel scanner | `sharp.trim()` | trim() uses libvips's flood-fill with threshold — handles anti-aliasing, JPEG compression artifacts, and near-white shadows correctly |
| Canvas compositing | Manual pixel buffer manipulation | `sharp.composite()` | Handles alpha blending, PNG output, and memory correctly |
| Image download with timeout | Custom fetch wrapper | Already in `downloadImage()` | Exists and tested |
| Staged upload | Custom multi-part upload | Already in `uploadStagedImage()` | Exists and tested |

**Key insight:** The existing image infrastructure (download, upload, staged uploads) is solid — only `standardizeImage()` needs to be replaced with a three-step pipeline: trim → compute placement → composite to canvas.

## Common Pitfalls

### Pitfall 1: trim() removes too much on dark garments
**What goes wrong:** `trim()` detects the background color from the top-left pixel. If a supplier image has the garment starting in the top-left corner (edge case), trim may clip the garment itself.
**Why it happens:** The background detection anchor is always the top-left pixel.
**How to avoid:** Check that after trim the output dimensions are at least 30% of the original — if they're tiny, the trim went wrong. Fall back to `fit: contain` with a warning for that image.
**Warning signs:** `info.width < originalWidth * 0.3 || info.height < originalHeight * 0.3`

### Pitfall 2: Off-white or gradient backgrounds
**What goes wrong:** JPEG-compressed images from CSW have slight tonal variation in white areas. `threshold: 10` may leave a 1-pixel border.
**Why it happens:** JPEG compression adds slight chroma variation even to pure white.
**How to avoid:** Start with `threshold: 10`, increase to `threshold: 20` if visual inspection shows background border remaining. Add a post-trim `flatten({ background: '#ffffff' })` to merge any residual alpha.
**Warning signs:** Garment width/height barely changes after trim (< 2% reduction from original).

### Pitfall 3: Print area fractions need per-category validation
**What goes wrong:** The fractions in `GARMENT_RELATIVE_PRINT_FRACTIONS` are estimates — using them without visual validation will produce misaligned print boxes.
**Why it happens:** "Chest area starts 10% below neckline" is an approximation; actual garment anatomy varies.
**How to avoid:** After implementing the pipeline, run it on the two reference products (S05280 and L00550), render the print box overlay, and compare to the customer-facing print position. Adjust fractions until the box matches.
**Warning signs:** Customer reports print box misaligned in the builder UI.

### Pitfall 4: categoryGroup not available in processProductImages()
**What goes wrong:** `processProductImages()` currently doesn't receive the garment category — it just processes images generically. To derive print area coords, it needs to know if it's a top or hoodie.
**Why it happens:** The category was only needed in `buildVariants()` previously.
**How to avoid:** Pass `categoryGroup: CategoryGroup` as a parameter to `processProductImages()`. Update callers in `product-push.ts` (already has `categoryGroup` in scope).

### Pitfall 5: Side images shouldn't go through garment detection
**What goes wrong:** Side/lifestyle images may not have white backgrounds or centered garments. Running trim on them produces unpredictable placement.
**Why it happens:** Trim assumes top-left pixel is background — not true for all image types.
**How to avoid:** Only apply garment detection (trim + placement) to `front` and `back` keys. Side images continue to use simple `fit: contain` resize.

## Open Questions

1. **Exact garment-relative print fractions**
   - What we know: the reference images (S05280, L00550) were measured to produce the current hardcoded coordinates
   - What's unclear: the exact fraction of garment height/width that maps to the chest print zone — this must be measured from those reference images once the pipeline is running
   - Recommendation: implement the pipeline with placeholder fractions, add a `--debug-coords` flag that overlays the print box on the output image, validate visually before committing constants

2. **Hoodie pouch area exclusion**
   - What we know: hoodie front print boxes should avoid the kangaroo pocket (lower ~25% of front garment)
   - What's unclear: whether the current fraction estimates already account for this
   - Recommendation: validate against L00550 reference hoodie with overlay rendering

3. **Long Sleeve raglan sleeves**
   - What we know: raglan sleeves create diagonal seam lines that trim() does not remove (they're part of the garment)
   - What's unclear: whether the wider sleeve silhouette changes the garment aspect ratio enough to affect print box placement
   - Recommendation: test one raglan product after implementing — if the chest zone fraction is wrong, add a 'raglan' sub-category
